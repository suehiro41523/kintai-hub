# ticket-create

## これは何のためのスキルか

このスキルの目的は「チケットを書くこと」ではなく、**「チケットを読んだ人が、何も聞かずに完了条件を判定できる状態にすること」**。書き手（Claude）と話した本人は背景を分かっているが、チケットは後で本人以外（未来の自分も含む）が読む。その人が客観的に「これは終わったか、終わっていないか」を判定できなければ、チケットとして機能していない。

だから、このスキルの仕事は実質的に**ヒアリング**である。ユーザーが最初に言う内容は大抵、背景か問題かどちらかに偏っていて、完了条件が曖昧なまま、あるいは全く無いまま出てくる。それを埋めるために質問をする。情報が無いところを推測で埋めない。推測で埋めると、完了条件が「客観的に判定可能」ではなくなり、このスキルの目的そのものが崩れる。

## チケットの構成要素

最終的に生成するMarkdownは、以下の4要素を持つ。

1. **タイトル**：何をするか/何が問題かが一目で分かる短い文
2. **背景・課題**：なぜこのチケットが必要になったか。何に困っているか、何が起きているか
3. **完了条件**：どうなればこのチケットを閉じられるか。チェックリスト形式で、各項目は「見ればYes/Noが分かる」文にする。**チェックボックスは必ず未チェック（`- [ ]`）で提示する**（下記参照）
4. **スコープ外**：今回はやらないこと（任意だが、粒度を揃えるのに効く。下記参照）

## ヒアリングの進め方

会話の流れからすでに分かっている情報は聞き直さない。これまでの会話で背景や問題がすでに語られているなら、それを引用・要約してユーザーに確認するだけでよい。欠けている要素だけを埋める。

ヒアリングで特に気をつけること：

- **完了条件は一番詰めが甘くなりやすい。** ユーザーが「〇〇を改善する」「〇〇を直す」としか言わない場合、それだけでは完了条件にならない。「改善した」をどう確認するか、誰が見ても同じ結論になる基準は何か、を聞く。例：「パフォーマンスを改善する」→「ダッシュボードの初期表示が2秒以内に完了する」のように、測定可能・観測可能な状態まで落とし込む
- **背景が無いチケットは、後で「なぜこれをやったんだっけ」が分からなくなる。** 「誰が困っているか」「何がきっかけでこの話になったか」を一言でも拾う
- **一度に全部聞かない。** 分かっていないことが複数あっても、チケットの骨格（タイトル・一言で言うと何か）がまず分かる質問から始め、会話の自然な流れで完了条件・スコープを詰めていく
- **ユーザーが即答できない質問は、一緒に考える。** 「完了条件は？」と聞いて困っているようなら、「じゃあ逆に、どうなったら困らなくなりますか？」のように角度を変えて聞く

## 完了条件は未チェックで出す

ヒアリングした時点で「もう作業は終わっている」とClaude自身が知っていても、完了条件のチェックボックスは**必ず未チェック（`- [ ]`）のまま**提示する。チェック済みにしない。

理由：チケットは、今この会話をしている本人（Claude・ユーザー）以外が後から読んで引き継ぐ可能性がある。その人は今日の会話を知らないし、今日の自分のローカル環境の状態も知らない。チェック済みの項目があると、それが「ローカルでは確認したが、誰でも検証できる形では残っていない」ものなのか、「客観的に検証可能な根拠（マージ済みPR、デプロイ済みURL等）がある」ものなのかが区別できず、完了条件という仕組みそのものの信頼性が崩れる。

作業が実際に完了していることが分かっている場合でも、チェックを入れるかどうかはユーザーに確認してから判断する（Claudeが自動で判断しない）。

## 粒度を揃える

チケットの粒度（大きさ・詳細度）が毎回違うと、後で並べた時に扱いづらくなる。目安：

- **完了条件は1チケットあたり3〜5項目程度に収まるのが健全。** ヒアリングの結果、完了条件が7項目を超えそうになったり、互いに無関係な内容が混ざっている場合は、「これは複数のチケットに分けたほうが扱いやすいかもしれません」とユーザーに提案する。無断で分割しない（ユーザーが意図的に1つの大きな塊として管理したい場合もあるため）
- **完了条件が1つも書けない話は、まだチケットになる段階ではない。** その場合は無理にチケット化せず、「もう少し方針を詰めてからチケットにしましょうか」と伝える
- **「スコープ外」を明示すると、知らないうちにチケットが肥大化するのを防げる。** ヒアリング中に話が広がってきたら、「それは今回のチケットに含めますか、それとも別チケットかスコープ外にしますか」と都度確認する

## 出力フォーマット

ヒアリングが終わったら、以下の形のMarkdownをコードブロックで提示する（GitHub Issuesにそのまま貼れる形）。

```markdown
# <タイトル>

## 背景・課題
<なぜこれが必要か。誰が何に困っているか>

## 完了条件
- [ ] <客観的に判定できる条件>
- [ ] <客観的に判定できる条件>

## スコープ外
<今回やらないこと（無ければこの章は省略してよい）>

## 補足
<参考リンク、関連する過去チケット、技術的な制約など（無ければ省略）>
```

提示した後、必ず一声かける：「この内容で起票してよさそうですか？足りない情報や、分割したほうがいい点があれば教えてください」。承認が取れるまでチケットを確定扱いにしない。

## ラベル

Markdownの提示と同時に、付けるラベルも提案する。

1. `gh label list --repo suehiro41523/kintai-hub`で**その都度最新のラベル一覧を取得する**（前回の会話で見た一覧を覚えていても、使い回さない。ユーザーや他の作業で増減している可能性があるため）
2. 取得した一覧の中から、チケットの内容に合うものを選ぶ。基本はこれで足りるはずなので、まず既存ラベルで済ませられないかを考える
3. どれも当てはまらない場合だけ、新しいラベルを提案してよい。その際は名前・説明・色（16進カラーコード）を示し、**「新しいラベル『<名前>』を作っていいですか」と明確に確認を取ってから**、`gh label create`を実行する。確認なしに新規ラベルを作らない
   ```bash
   gh label create "<ラベル名>" --repo suehiro41523/kintai-hub --description "<説明>" --color "<16進カラーコード>"
   ```

## GitHubへの起票

ユーザーの承認が取れたら、`gh` CLIで実際にissueを作成し、プロジェクトボードに追加する。ラベルは`--label`で指定する（複数ある場合は`--label`を複数回指定する）。

```bash
gh issue create --repo suehiro41523/kintai-hub --title "<タイトル>" --body "<背景・課題〜補足までの本文>" --label "<ラベル名>"
```

出力されたissue URLを使って、プロジェクトボードに追加する。

```bash
gh project item-add 1 --owner suehiro41523 --url <issueのURL>
```

- プロジェクト：`kintai-hub ticket manager`（owner: `suehiro41523` / プロジェクト番号: `1`）
- リポジトリ：`suehiro41523/kintai-hub`

**承認を取る前に、`gh issue create`・`gh project item-add`・（新規ラベルがある場合は）`gh label create`を実行しない。** いずれもGitHub上に残る、他者から見える操作なので、ユーザーが明示的に許可した内容（本文・ラベル）と実行するコマンドの内容が一致していることを確認してから実行する。実行後は作成されたissueのURLをユーザーに共有する。

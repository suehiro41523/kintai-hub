## 0. 前提・スコープ

- [top-page-design.md](./top-page-design.md) で定義した「無料で始める」CTAの遷移先。トップページ→本画面→メール認証→ダッシュボードという **セルフサーブ登録フロー** の入口を担う。
- 呼び出すAPIは `api-spec.md` に既に定義済みの `POST /auth/sign-up`（`name, email, password, company_name, plan` → `{ user, tenant, session_token }`）をそのまま利用する。新規エンドポイントの追加は不要。
- 料金プラン選択UIは[top-page-design.md 今後の検討事項](./top-page-design.md#8-今後の検討事項未確定)で「今回スコープ外」と決定済みのため、本画面でも **プラン選択UIは表示しない**。`plan` は `'free'` を固定値としてリクエストに含める。
- デザイントーンは `/login`（`apps/web/src/app/login/page.tsx`）を踏襲し、テナント管理者候補が迷わず離脱しない最短フォームとする。

---

## 1. 目的・ゴール

| 項目 | 内容 |
|---|---|
| 画面の役割 | 会社情報＋管理者アカウントを1フォームで受け取り、テナントを即時作成する |
| 完了条件 | `POST /auth/sign-up` 成功 → `/verify-email` へ遷移 |
| 離脱防止方針 | 入力項目を最小限（4項目＋同意チェック）に絞り、複数ステップ化しない（1画面完結） |
| 想定所要時間 | 1分以内 |

---

## 2. 画面遷移

```
[トップページ /] 「無料で始める」
   ↓
[/signup]（本画面）
   ├─ 送信成功 → [/verify-email]（メール認証待ち）
   ├─ 送信失敗（バリデーション） → 同画面内にエラー表示、再入力
   └─ 送信失敗（409: メール重複） → 同画面内にエラー表示 + [/login] への導線を提示
   ↓
「すでにアカウントをお持ちですか？」リンク → [/login]
```

## 3. レイアウト構成

`/login` と同一の骨格（中央寄せ・単一カード）を採用し、視覚的な一貫性を持たせる。

```
┌─────────────────────────────────────┐
│  [Clockアイコン] KintaiHub            │ ← ロゴ（/loginと共通コンポーネント化）
│                                       │
│  ┌─────────────────────────────┐    │
│  │ 無料でアカウントを作成         │    │ ← 見出し
│  │                               │    │
│  │ 会社名           [________]  │    │
│  │ お名前           [________]  │    │
│  │ メールアドレス    [________]  │    │
│  │ パスワード        [________]  │    │
│  │ パスワード（確認） [________]  │    │
│  │ ☐ 利用規約とプライバシー      │    │
│  │   ポリシーに同意する           │    │
│  │                               │    │
│  │ [     無料で始める     ]      │    │ ← primaryボタン（blue-600）
│  └─────────────────────────────┘    │
│                                       │
│  すでにアカウントをお持ちですか？      │
│  ログイン →                          │
│                                       │
│  クレジットカード登録不要             │ ← 補足テキスト（slate-400）
└─────────────────────────────────────┘
```

- カード幅：`/login` と同じ `max-w-sm` だと項目数的に窮屈なため **`max-w-md`** に拡張する（他は `bg-white rounded-xl shadow-sm border border-slate-200 p-6` を踏襲）。
- モバイル：カードは画面幅いっぱい（左右 `px-4`）、縦積みは変わらず。

## 4. フォーム項目定義

| # | 項目 | input type | 必須 | 対応API/DBフィールド | プレースホルダー例 |
|---|---|---|---|---|---|
| 1 | 会社名 | text | ○ | `company_name` → `core.tenants.name` | 株式会社サンプル |
| 2 | お名前 | text | ○ | `name` → `core.users.name` | 山田 太郎 |
| 3 | メールアドレス | email | ○ | `email` → `core.users.email`（ログインID） | admin@example.com |
| 4 | パスワード | password | ○ | `password`（Better Auth経由） | 8文字以上 |
| 5 | パスワード（確認） | password | ○ | フロントのみ（API送信なし・一致検証用） | — |
| 6 | 利用規約同意 | checkbox | ○ | フロントのみ（API送信なし・送信ボタン活性化条件） | — |
| （非表示固定値） | プラン | — | — | `plan = 'free'`（UI非表示、送信時に固定付与） | — |

`role='admin'` はAPI側で「サインアップ経由の初回ユーザーは常にadmin」として自動決定するため、フロントからは送信しない（`api-spec.md`のレスポンス例 `{ user, tenant, session_token }` の `user.role` がサーバー側で `admin` 固定になる想定。この点はAPI実装時に要すり合わせ）。

## 5. バリデーションルール

フロント側は React Hook Form + Zod（`TECH-STACK.md` 準拠）でクライアントバリデーションを行い、サーバー側の `VALIDATION_ERROR`（`API-PATTERNS.md`のエラー形式）をそのままフィールド単位で表示する二段構え。

| 項目 | ルール | エラーメッセージ例 |
|---|---|---|
| 会社名 | 1〜255文字（`core.tenants.name` は VARCHAR(255)） | 「会社名を入力してください」/「255文字以内で入力してください」 |
| お名前 | 1〜100文字（`core.users.name` は VARCHAR(100)） | 「お名前を入力してください」 |
| メールアドレス | email形式 / 255文字以内 | 「メールアドレスの形式が正しくありません」 |
| パスワード | 8文字以上（提案値・確定要） | 「パスワードは8文字以上で入力してください」 |
| パスワード（確認） | パスワードと一致 | 「パスワードが一致しません」 |
| 利用規約同意 | チェック必須 | 「利用規約とプライバシーポリシーへの同意が必要です」（送信ボタンはチェックまで非活性） |

**サーバー側エラーとの対応**

| APIエラー | 表示箇所 |
|---|---|
| `400 VALIDATION_ERROR` | `details[].field` に対応するフィールド直下にインラインエラー表示 |
| `409 CONFLICT`（メールアドレス重複） | フォーム上部にバナー表示：「このメールアドレスは既に登録されています。ログインしますか？」+ `/login` リンク |
| `429 RATE_LIMITED` | フォーム上部にバナー表示：「試行回数が上限に達しました。しばらくしてから再度お試しください」 |
| その他 5xx | フォーム上部に汎用エラー「エラーが発生しました。時間をおいて再度お試しください」（`/login` の実装パターンを踏襲） |

## 6. 送信フロー

```
ユーザーがフォーム入力 → 「無料で始める」クリック
   ↓
フロント: Zodスキーマでクライアントバリデーション
   ↓（NG）フィールドごとにエラー表示、送信中断
   ↓（OK）
ボタンを「登録中...」表示＋disabled（/loginのisPendingパターンを踏襲）
   ↓
POST /api/v1/auth/sign-up
  { company_name, name, email, password, plan: 'free' }
   ↓（失敗）5章のエラーハンドリングに従い表示、ボタンを再活性化
   ↓（成功）
{ user, tenant, session_token } を受信
   ↓
router.replace('/verify-email') へ遷移
```

- 既存 `useSignIn`（`apps/web/src/hooks/useAuth.ts`）に倣い、`useSignUp` フックを新設して TanStack Query の `useMutation` でラップする。

## 7. 状態別UI

| 状態 | UI |
|---|---|
| 初期表示 | 全フィールド空、送信ボタンは活性（クリック時にクライアントバリデーション） |
| 送信中 | 送信ボタンを「登録中...」+ `disabled`、他フィールドは編集可能のまま（`/login`と同パターン） |
| バリデーションエラー | 該当フィールド下に赤文字（`text-red-600`）でメッセージ表示 |
| 送信失敗（サーバーエラー） | フォーム上部にバナー表示、フィールド内容は保持（再入力不要） |
| 送信成功 | `/verify-email` へ即遷移（本画面上に成功メッセージは出さない） |

## 8. 関連画面：メール認証待ち（/verify-email）

サインアップ完了後の着地点として最低限の要件のみ定義する（詳細設計は別途）。

- 表示内容：「確認メールを送信しました。メール内のリンクをクリックして認証を完了してください」＋登録したメールアドレスの表示
- 「メールが届かない場合」→ 再送信ボタン（レート制限あり）
- メール内リンク踏了後の遷移先：`/clock`（初回ログイン状態としてダッシュボードへ）

## 10. アクセシビリティ・その他

- 各 `input` に対応する `label` の `htmlFor` を必ず設定（`/login` の既存実装パターンを踏襲）
- パスワード欄に表示/非表示切り替えトグルを設置（8文字以上の入力ミス防止）
- 送信ボタンは `type="submit"`、Enterキーでの送信に対応（`/login` と同様に `<form onSubmit>` で実装）
- 利用規約・プライバシーポリシーのリンク先ページは本書のスコープ外（[top-page-design.md 8章](./top-page-design.md#8-今後の検討事項未確定)の法務コンテンツ整備を待つ。リンク切れ防止のため実装時点では別タブ表示のプレースホルダーページで可）

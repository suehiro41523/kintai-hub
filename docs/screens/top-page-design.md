# top-page-design.md — トップページ設計書

> バージョン: 1.2 / 作成日: 2026-08-03 / 更新日: 2026-09-22 / ステータス: ドラフト
> 目的: 新規アカウント作成導線の実装に向けたトップページ（LP）の構成設計

**2026-09-22 方針転換**: 「SES業界特化」の訴求から、「複数の業務・契約をまたいで稼働する業種向け」の訴求へ転換した。要件定義書§3は元々SESを唯一のターゲットとは規定しておらず（「SES・派遣・受託など…業種向け」という書きぶり）、DBスキーマ（`app.work_types`）も業種非依存の汎用設計だったため、転換に伴うスキーマ・ドメインルール側の変更は無い。訴求構造も「業務ごとに可視化→精算が必要な業務は金額まで自動計算」という因果関係のある1本のストーリーに再構成した（可視化=土台、精算自動化=差別化の本体。詳細は4.4参照）。

## 0. 前提・スコープ

- 現状 `apps/web` には `/login` のみ存在し、新規アカウント作成の導線（トップページ・サインアップページ）が存在しない。本書はその新規導線の設計書。
- サインアップ方式：**セルフサーブ即時登録**。トップページのCTAから直接テナント（企業）作成・管理者アカウント作成まで到達し、営業担当の介在なしに即日利用開始できることをゴールとする。
- 訴求ターゲット：**複数の業務・契約をまたいで稼働する業種**（SES・派遣・受託開発・コンサルなど、具体例を列挙して訴求。SES限定ではない）。主に人事・総務・経理担当（決裁権を持つ管理部門層）に語りかける。要件定義書 [3. 差別化機能](../requirements.md) を主軸に、「ワークタイプごとの可視化→精算自動化」というストーリーで訴求する。
- **料金プランセクションはスコープに含める**（2026-09-22更新）。`core.tenants.plan` のfree/standard/pro/enterpriseに対応する仮の金額・上限を4.9.5で定義する。CTAは「無料で始める」とし、登録時点では `plan = 'free'` を暗黙に割り当てる想定。
- ブランドは**新規に作り直す**（2026-09-22更新）。既存 `/login` ページ（`apps/web/src/app/login/page.tsx`）の `blue-600` + Clockアイコン構成は廃止し、ネイビー・深青系の新配色に刷新する。ログイン画面側は本LP刷新後に追従して差し替える想定（別タスク）。
- 社会的証明（顧客ロゴ・導入実績・数字）は**使用しない**。ローンチ前で実績がゼロのため、信頼性訴求はセキュリティ・データ保護面（4.8参照）で代替する。
- コピーの語調は既存のカジュアルな共感トーン（例：4.2「まだExcelで集計していませんか？」）を維持する。エンタープライズ的な信頼感は文体ではなく、配色・レイアウト・余白などビジュアル面で表現する。

## 2. ターゲットユーザー（要件定義書 1.3 準拠）

トップページで主に語りかける相手は **導入意思決定者＝テナント管理者候補**。他ロール（マネージャー・一般ユーザー）は「導入後にこう使う」の文脈で補足的に登場させる。

| ロール | トップページ上の扱い |
|---|---|
| テナント管理者（HR/バックオフィス） | メインターゲット。課題提起・差別化機能・CTAはすべてこの層向け |
| マネージャー | 「チームの承認がラクになる」という機能紹介の一部として登場 |
| 一般ユーザー（従業員） | 「打刻がシンプル」という機能紹介の一部として登場 |
| スーパー管理者 | トップページ上には登場させない（自社内部ロールのため） |

### 4.3 課題提起セクション（Before）

要件定義書 [3.1 背景・課題](../requirements.md) の4項目を、業種を問わない表現でカード化（2026-09-22更新：「客先A」等SES限定の語彙を一般化）。

| 課題カード | 見出し | 説明 |
|---|---|---|
| 1 | 稼働区分が混在して打刻できない | 「同日に社内業務2h＋客先常駐4h」を今の勤怠システムで区別できますか？ |
| 2 | 精算計算が手作業 | 精算が必要な業務の稼働時間をExcelで集計、ミスと工数が発生していませんか？ |
| 3 | 原価が見えない | 自社業務と客先・プロジェクト業務のコスト配賦、感覚値になっていませんか？ |
| 4 | 多契約の並行管理が煩雑 | 複数の契約・業務に同時アサインされている社員の管理、大変ではありませんか？ |

トーン：責めるのではなく「あるある」に共感する見出し（疑問形）。

### 4.4 差別化機能セクション（★ワークタイプ連動の可視化・精算）

要件定義書 [3.2 ワークタイプ定義](../requirements.md) / [3.3 精算モデル](../requirements.md) をベースに、製品の核心価値をストーリー仕立てで説明する最重要セクション。

**2026-09-22更新**: 「可視化」と「精算自動化」を並列の2主張にせず、因果関係のある1本のストーリーに再構成。可視化はどの業種にも当てはまる土台、精算自動化はSES・派遣・受託開発など精算が必要な業種に効く差別化の本体（TimeCrowd等の汎用時間記録ツールには無い機能）。

0. **リード文**：「打刻するだけで、業務ごとの稼働がそのまま可視化されます。客先請求などの精算が必要な業務は、設定した精算ルールに従って金額まで自動計算。社内業務・営業活動など精算が不要な業務は、可視化・レポートだけのシンプルな使い方もできます。」
1. **概念図**：1人の従業員が1日の中で「原籍業務→客先常駐→移動」と打刻を切り替えるタイムライン図（`app.work_types.color` を使った色分け表現）
2. **ワークタイプ設定例（業種横断）**：SES・受託開発「原籍業務／客先常駐」、営業「社内業務／外回り（精算なし＝可視化のみ）」、コンサル「プロジェクトA／プロジェクトB」など、複数業種の設定例をカードで併記し、SES限定ではないことを明示
3. **精算方式の柔軟性**：完全固定／時間精算／上下幅あり／プロジェクト の4方式に対応することを、アイコン付き4カードで訴求。「精算なし」を選べば可視化のみのワークタイプとしても使える旨を補足
4. **Before/After比較**：「Excel手集計」→「打刻するだけで業務ごとの可視化から精算まで自動化」を1枚の対比図で見せる

### 4.7 導入の流れセクション

セルフサーブの手軽さ＝営業を介さず即日使える点を明示し、CTAへの心理的ハードルを下げる。

| ステップ | 内容 |
|---|---|
| 1 | 「無料で始める」から会社名・管理者メールアドレス・パスワードを入力（1分） |
| 2 | メール認証（届いたリンクをクリック） |
| 3 | ワークタイプを登録（原籍業務・客先名など、テンプレートから選択可） |
| 4 | 従業員を招待して打刻開始 |

CTA：このセクション末尾にも「無料で始める」ボタンを再掲。

### 4.8 信頼性・セキュリティセクション

法人担当者が導入前に気にする点を先回りして解消（要件定義書 4章 非機能要件を根拠に）。

- テナントごとにデータを完全分離（PostgreSQL RLSによるマルチテナント分離）
- 通信・保存データを暗号化（TLS1.3 / AES-256）
- 操作ログを5年保管、法令準拠の監査ログ（`audit_logs`は改ざん不可＝UPDATE/DELETE禁止）
- 稼働率99.9%以上のSLA目標

### 4.9 料金プランセクション（2026-09-22追加）

社会的証明（顧客実績）が使えない分、透明性の高い価格提示で信頼を補う。4プランを横並びカードで表示し、`Standard` を「人気」バッジで推奨表示する。金額は仮値であり、正式なプライシング検討後に確定する。

| プラン | 月額（税別） | 対象規模 | 内容 |
|---|---|---|---|
| Free | ¥0 | 〜5名 | 基本打刻・シフト・レポート、ワークタイプ1種まで |
| Standard（人気） | ¥400 / 人 | 6〜50名 | ワークタイプ連動精算フル機能、申請ワークフロー、給与ソフト連携 |
| Pro | ¥700 / 人 | 51〜300名 | 複数精算方式並行、優先サポート、API連携 |
| Enterprise | 個別見積もり | 301名〜 | SSO、専任サポート、SLA保証 |

- 各カードにCTA：Free/Standard/Pro→「無料で始める」、Enterprise→「お問い合わせ」
- 補足：「すべてのプランでワークタイプ連動精算の基本ロジックは共通。人数・機能で選べます」

## 5. セルフサーブ・サインアップフロー設計

トップページCTAの遷移先として、以下のフローを想定する（詳細実装は別途API設計が必要）。

```
[トップページ] 「無料で始める」クリック
   ↓
[/signup] サインアップフォーム
   - 会社名（→ core.tenants.name）
   - 管理者氏名（→ core.users.name）
   - 管理者メールアドレス（→ core.users.email）
   - パスワード（Better Auth経由）
   ↓ 送信
バックエンド処理（トランザクション、CODING-RULESルール4準拠）
   1. core.tenants を1件作成（plan='free', status='active'）
   2. core.users を1件作成（role='admin', tenant_id=作成したテナントID）
   3. Better Auth側にcredentials登録
   4. 確認メール送信（Resend）
   ↓
[/verify-email] メール認証待ち画面 → メール内リンク踏了後 → 認証完了
   ↓
[/onboarding] 初期設定ウィザード（任意）：ワークタイプ登録の簡易ガイド
   ↓
[/clock]（既存ダッシュボード）へ遷移、以降は通常ログインフロー
```

**設計上の論点（本書では未確定・実装時に要判断）**

- `core.tenants` に無料プランの利用期限管理カラム（例：`trial_ends_at`）が現状無い。将来的にトライアル期限を設ける場合はスキーマ追加が必要。
- 会社名の重複チェック・メールアドレスの一意性チェック（`core.users.email` は既にUNIQUE制約あり）。
- サインアップ直後にワークタイプが1件も無い状態でどう打刻画面を見せるか（空状態のUX）。
